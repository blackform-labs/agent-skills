# Reviewing a UI against its intended design

Identify the user task, platform, supported environments and reference for the intended result. Use the applicable Material guidance, platform interaction or accessibility specification, project design contract, approved reference view, or explicit user requirement. Attribute each finding to its actual source. A discretionary visual improvement can be proposed as a design suggestion.

| Area | What to inspect or exercise | Reference |
| --- | --- | --- |
| Composition and visual hierarchy | Compare the first point of attention, reading order, grouping, alignment and rhythm with the main task and approved design. Inspect the whole view and adjacent elements. | [Expressive tactics](https://m3.material.io/blog/building-with-m3-expressive), [layout](foundations/layout.md) |
| Typography, color and surfaces | Inspect text roles, wrapping and truncation with realistic content. Compare foreground/background roles, contrast, theme changes, icon legibility, elevation and surface boundaries in the rendered state. | [Applying type](https://m3.material.io/styles/typography/applying-type), [color roles](https://m3.material.io/styles/color/roles), [shape](https://m3.material.io/styles/shape/overview-principles) |
| Component choice, anatomy and dimensions | Match each control to the action it performs. Inspect labels, icons, selection indicators, shape and hit area. Compare the relevant sizes and states using the component sheet and the official guidelines. | [Component index](components/index.md) |
| Navigation, content and task behavior | Follow entry, action, back or cancel, and completion. Check whether labels predict the outcome, destinations remain identifiable, and feedback reflects actual application state. Exercise empty, loading, success, error and recovery paths where the flow supports them. | Project flow and content requirements, [component guidelines](https://m3.material.io/components) |
| Accessibility and input | Inspect accessible names, roles, values and relationships. Exercise keyboard traversal and activation, focus entry and return, visible focus, pointer or touch operation, and status announcements as applicable. Distinguish accessibility-tree inspection from an actual screen-reader test. | [Material accessible design](https://m3.material.io/foundations/accessible-design/overview), [W3C accessibility criteria for web](https://www.w3.org/TR/WCAG22/) |
| Adaptive layout | Check the relevant widths and input modes with realistic long labels, text enlargement or localization. Inspect clipping, overflow, overlap, obscured controls and reading order across layout changes. | [Material layout](https://m3.material.io/foundations/layout/layout-overview/parts-of-layout), project-supported configurations |
| Motion and continuity | Exercise state transitions, interruption, repeated actions and reduced-motion settings when applicable. Compare position, opacity, duration and focus after the transition settles. | [Material motion](https://m3.material.io/styles/motion/overview/how-it-works), platform and project motion guidance |

A screenshot can establish an overlap or weak visual hierarchy. Runtime behavior needs interaction evidence. If a criterion applies but evidence is missing, identify the specific check still needed. If a local pattern has no Material equivalent, evaluate its usability against the user task and project or platform contract. Report the smallest scoped correction and a verification step for each confirmed discrepancy.
